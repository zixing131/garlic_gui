# Garlic GUI 0.5.28（C++ / Qt 6）

原生桌面浏览器，使用本项目的 garlic C 引擎。Qt 界面通过 `QProcess` 调用引擎，
先建立类型、成员和引用索引，点击类时生成 Java / Smali。索引读取 CLASS / DEX
元数据与引用，不执行方法反编译。JAR 索引会读取其中的 CLASS 内容。

## 0.5.28 Windows 测试设置初始化

- 修复 Windows x64 / ARM64 的字体和语言测试失败：在任何设置读写前初始化测试应用身份，确保原生 QSettings 可用。
- 每次窗口测试运行使用独立设置空间，每个用例重置设置，并显式校验设置写入状态，避免测试顺序和旧配置干扰快捷键验证。

## 0.5.27 搜索与引用精确定位

- 搜索结果保存完整命中行、出现次序和匹配范围，跳转选中具体内容，兼容正则、长行、CRLF 及界面补入的 `@Override`。
- 引用按真实符号和出现次序定位，避免同名类成员或同一行的其他单词被选中；源码尚未生成时，在加载后的所属方法内解析目标。
- 待跳转请求绑定目标 Java 页面；资源异步预览采用最后一次点击的位置。

## 0.5.26 字体设置与多语言

- 设置 → 界面可分别选择 UI、代码/脚本编辑器、Smali/Hex 的字体和字号（8–48 pt），支持系统默认字体。字体保存后即时应用，不重建左侧目录；行号栏、Tab 宽度与 Hex 滚动范围同步更新。旧代码字号设置自动迁移。
- 语言支持简体中文、繁体中文、英文、俄文、法语、日语和韩语，重启生效。首批翻译覆盖主菜单、设置控件、导航、搜索、引用和脚本等常用界面；引擎日志及部分专业说明仍保留原文。
- `languages/*.json` 使用 UTF-8，新增文件即可扩展语言，不需重编译。缺失译文回退到原文。格式见随构建和发行包附带的 `languages/README.md`；macOS 可在 `.app` 旁放置 `languages/` 覆盖内置语言文件。
- 快捷键按稳定 ID 保存，切换语言不会丢失，并兼容读取原简体中文快捷键设置。
- GUI/headless 共用版本号，`garlic` 是独立的 C 引擎子进程。保留进程边界以隔离解析崩溃、支持强制取消并回收引擎内存；源码和索引缓存命中时不启动引擎。单纯合并可执行文件不会消除解析成本。直接在 GUI 进程内调用需先移除引擎全局状态、exit 路径并实现可重入上下文，本次不做直接内嵌。

## 0.5.20 持久源码缓存

- 补齐此前只持久化查询索引/JSONL 的缺口：磁盘模式保存按类生成的 Java、Smali 及源码定位映射，全量生成成功后保存 Java 源码包、映射包及其目录索引。重新打开直接读取完成的源码缓存，不启动重复反编译；代码搜索也使用恢复的源码目录。
- 源码与查询索引共用设置中的缓存目录和默认 20 GiB 总预算，空间不足时淘汰最老缓存。设置显示索引数、源码缓存组数和合计占用。“清理当前源码缓存”也清理当前输入/配置的持久源码；清除目录中的缓存会同时删除索引和源码。
- 输入内容、引擎/GUI 版本、反混淆、排除包以及 Unicode/控制流恢复配置变化会隔离缓存，内存模式不保存持久源码。只有完整生成并成功保存的结果可恢复；文件缺失或长度异常时按需重新生成，不把中断的全量生成当成完成。
- 打开时不递归扫描源码目录或复制全量源码包；直接读取缓存文件，保持索引快速恢复。日志出现“源码缓存已保存（含定位映射）”后可供下次使用；升级前没有持久保存的源码仍需生成一次。
- 本机微信 8.0.76 实测：关闭旧会话后，索引与全量源码恢复 **4.53 秒**；首次读取缓存 LauncherUI Java 及 **7,522 个定位片段**约 **0.32 秒**，未启动反编译进程。索引、JSONL 和全量源码合计约 **4.20 GiB**；未强制清空系统文件缓存。
- 回归覆盖删除旧临时工作区后恢复 Java/Smali、定位映射一致性、完整 DEX/APKS 源码包、JAR/CLASS 源码目录、缓存代码搜索不启动引擎、配置隔离和清理行为。

## 0.5.19 并行恢复磁盘索引

- 缓存改为独立校验的数据块：固定头部校验后，并行校验/解析各块，通过文件映射共享只读页面，避免恢复前串行扫描整份快照。数据块缺失、截断、长度异常或内容校验不符均回退到重新建索引。
- 类与成员表直接保留四个哈希分区，不再在恢复后合并数百万条记录；成员查询数组与类/引用块并行准备。快照保留已计算的别名版本摘要，不再每次打开都重新遍历和校验全部别名。
- 微信 8.0.76（236,037 类，开启自动别名）本机实测：新进程完整缓存恢复 **3.55 秒**、同一进程再次打开 **3.80 秒**；实际 MainWindow 测试中目录和完整索引同时就绪 **3.42 秒**，首次 LauncherUI Java **0.76 秒**，最大界面心跳间隔 **235 毫秒**。对比 0.5.18 的 12.40 秒，恢复已进入 5 秒内；未强制清空操作系统文件缓存，其他机器/存储介质需分别实测。
- 旧项目释放使用低优先级后台任务，避免重开时与索引恢复争抢 CPU；嵌套元数据临时目录在父工作区仍受保护时清理，避免并发清理警告。
- 新增分块损坏/截断/额外字节/取消回归，真实 APK 对比恢复前后的引用和别名。`GARLIC_TEST_CACHE_DIRECTORY` 可指定可复用的基准缓存目录，`realWarmCache` 分别测量新进程和同进程恢复。
- 所有数据块及查询表完成后才报告索引就绪；没有把引用查询初始化推迟到第一次查询。新缓存格式需要重新建立一次，旧格式会自动失效。完整 JSONL、20 GiB 容量、目录选择与清理策略保持可用。

## 0.5.18 持久索引与目录设置

- 设置 → 缓存：磁盘模式会保存完整类/成员/引用查询索引、自动别名和原始 JSONL，默认容量 **20 GiB**。可修改“索引缓存目录”和容量；目录留空使用系统缓存目录下的 `garlic/indexes`。macOS 默认是 `~/Library/Caches/garlic/indexes`。
- 新索引保存时，按创建时间删除最老的完整缓存，直到满足容量和磁盘可用空间要求；单个索引超过上限时不缓存，不影响当前分析。设置中显示索引数量/占用，可清除所选目录；修改目录不自动搬迁旧文件，可选回旧目录清理。
- 文件菜单新增“重建当前文件索引”。普通打开验证输入文件内容、引擎版本和索引配置后复用快照；输入、引擎、自动别名或排除配置变化，以及快照损坏/缺失时自动重新建立。内存缓存模式不保存持久索引。
- 索引在后台保存，日志提示“磁盘索引已保存（含 JSONL）”后可供下次重用。退出/取消时不等待保存；中断的缓存不会被当作完整索引。清除缓存也会使旧的待写入任务失效，防止清理后旧任务又写回。仅清理 Garlic 管理的缓存条目，不删除目录内其他文件。
- 首次加载时引用构建与自动别名并行；没有对应缓存时不阻塞类目录显示去计算文件内容校验。恢复时批量读取引用位置，使用 BLAKE2b 内容校验与 Qt JSON 解析；切换文件时在后台释放旧索引对象。
- 本机微信 8.0.76 开启自动别名实测（236,037 类）：首次目录 **0.68 秒**，完整索引 **16.16 秒**，缓存恢复完整索引 **12.40 秒**；此前版本完整索引约 20.4 秒。快照和 JSONL 合计约 2.53 GiB。这些是当前系统负载下单轮结果，**首次完整索引尚未达到 5 秒**。
- 新增持久化往返、配置/目录/输入失效、配额淘汰、损坏/取消恢复、孤立临时文件清理、重建及缓存命中后源码生成测试。可设置 `GARLIC_TEST_CACHE_APK` 运行 `garlic-gui-index-cache-tests realApkCache` 实测冷/热加载；完整首次加载尚未达到 5 秒。

## 0.5.17 嵌套 DEX ZIP 与并行索引

- 修复完整 DEX 索引只报告初始 0% 的问题，每处理完一个 DEX 更新进度。GUI 不再从日志尾部重复播放旧进度；大 ZIP（32 MiB 起）先加载类目录，再后台准备完整元数据，与大 APK 行为一致。
- ZIP 中的 `fix/...dex` 等嵌套路径保留为 DEX 来源，点开类时只处理来源 DEX；修复无包名类被写到虚构的 `default/` 目录并生成 `package default;`，Java/Smali 现在使用正确的根路径。
- 完整索引按类并行构建，128 类一批并按原顺序写出，保持重复类的覆盖顺序。每个任务使用独立内存池；DEX 索引写完后释放其解析内存，索引模式不初始化反编译专用结构。小引用组在栈内去重，大组继续使用哈希表。
- 本机 `mobi23.72.1_dex_fix.zip`（31 个嵌套 DEX，194,257 类）实测：目录约 0.53 秒，完整索引约 19.3 秒（关闭自动别名），`AUX` 源码约 0.46 秒。引擎完整 JSONL 生成从约 12.7 秒降到约 5.84 秒，修复前后完整文件 SHA-256 一致。
- 微信开启自动别名时目录约 0.69 秒，完整索引约 20.4 秒（上一轮约 24.1 秒），首次 LauncherUI Java 约 0.96 秒。元数据导入约 9.7 秒、别名约 3.9 秒、引用/符号查询索引约 6.0 秒；**完整加载尚未达到 5 秒**，结果随机器与系统负载变化。
- 新增嵌套 ZIP 进度/来源/源码、无包名 Java/Smali、单线程与多线程目录等价和引用去重回归。设置 `GARLIC_TEST_ARCHIVE` 可运行 `realNestedArchive` 验证真实大 ZIP。

## 0.5.16 引用过滤与反混淆性能

- 引用窗口新增二次过滤，按节点名称、代码片段进行不区分大小写的字面匹配；显示筛选/总数，新增结果与 Java 预览更新后自动重新匹配。复制、跳转和可见行预览均使用筛选后的结果，不重新查询索引。
- 引用节点图标直接查符号表，避免每条引用重新扫描所属类全部成员。批量导入复用未构建的引用索引；同名类映射不再逐次线性查重，继承符号解析跳过已确认不存在的起始候选。
- 自动别名生成对普通 ASCII 标识符走快速检查，保留 Unicode 和异常名称的原规则；反控制流处理跳过没有候选指令的方法，并通过已有类哈希索引定位辅助方法，保留求值与改写规则。
- 本机微信 8.0.76 单轮对比：完整元数据就绪约 42.9 → 24.1 秒，别名阶段约 10.3 → 3.8 秒，引用/符号查询索引阶段约 16.0 → 6.2 秒；类目录约 0.7 秒。机器存在其他大内存进程，耗时会波动，**完整加载尚未达到 5 秒**。

- `GARLIC_PROFILE_LOAD=1` 新增 metadata 解析、别名、查询索引分阶段计时，便于继续定位大 APK 瓶颈。

## 0.5.15 大项目响应与退出

- 修复开启反混淆后查询索引到 100% 长时间卡住：界面直接使用别名哈希表，差异计算移到后台，类树标签分批更新；保存别名 JSON 按排序后的键构建，避免随机插入的平方级开销。

- 本机微信 8.0.76（236,037 类）开启反混淆实测：类目录约 0.88 秒，元数据就绪约 25.7 秒，首次打开 LauncherUI Java 约 0.88 秒；最长界面心跳间隔约 359 毫秒，原索引完成后的数十秒卡顿消除。实际 GUI 加载中退出约 39 毫秒、索引完成后退出约 616 毫秒，均确认缓存清理完成。数据随机器、缓存状态变化；未在 Windows 实机复测。
- 新增真实 GUI 子进程退出/缓存清理回归；设置 `GARLIC_TEST_LIFECYCLE_APK` 可加入大 APK 测试。Qt 窗口测试的 `realLargeLifecycle` 支持 `GARLIC_TEST_DEOBFUSCATE=1` 检查反混淆索引发布和源码加载期间的界面响应。

## AI 无头模式与 MCP 自动接入

独立说明文件为 `AI-HEADLESS.md`。普通编译后位于 `build/gui/`；macOS 包内位于 `Contents/Resources/`，Windows/Linux 与可执行文件同目录；
发布包根目录也提供该文件，AI 无需访问源码仓库即可读取。

给 AI 软件目录和 APK/APKS 路径后，让它先阅读本 README，按以下步骤接入。
无头模式不创建窗口、不需要显示器，直接加载输入并提供与 GUI 共用的分析工具。

1. 在软件目录定位可执行文件：macOS 发布包为 `Garlic.app/Contents/MacOS/garlic-gui`，
   Windows 为 `garlic-gui.exe`，Linux 为 `garlic-gui`。源码构建的 macOS 路径是
   `build/gui/garlic-gui.app/Contents/MacOS/garlic-gui`。保留同目录的 `garlic` 引擎及 Qt 依赖。
2. 使用绝对路径生成 MCP 配置（路径包含空格时加引号）：

   ```sh
   "/软件目录/Garlic.app/Contents/MacOS/garlic-gui" --headless \
     --apk "/APK目录/app.apks" --threads 8 \
     --deobfuscate --simplify-control-flow --unflatten --print-mcp-config
   ```

3. 将输出的 `mcpServers.garlic` 项合并到 AI 客户端的 MCP 配置，保留原有服务。
   支持 JSON 配置的客户端可直接采用以下格式；其他客户端将 `command` 和 `args`
   映射到其 MCP 配置格式。无需先手动启动软件，客户端连接时会自动启动并打开指定 APK。

   ```json
   {
     "mcpServers": {
       "garlic": {
         "command": "/软件目录/Garlic.app/Contents/MacOS/garlic-gui",
         "args": ["--headless", "--apk", "/APK目录/app.apks", "--threads", "8",
                  "--deobfuscate", "--simplify-control-flow", "--unflatten"]
       }
     }
   }
   ```

4. 完成 MCP `initialize`，通过 `tools/list` 获取工具。调用 `get_status`，等待
   `class_count > 0` 且 `busy = false`，再调用 `get_all_classes`、`get_class_source`、
   `get_methods_of_class`、引用查询和搜索工具。类名使用列表返回的准确大小写。
   大型 APKS 的类列表先就绪，完整元数据稍后完成；依赖成员/引用的工具会等待元数据。
   暂时繁忙时稍后重试，不要反复重启进程。

可直接给 AI 的指令：

> 软件目录是 `/软件目录`，APK 路径是 `/APK目录/app.apk`。请读取软件目录下的
> README，定位可执行文件，用无头模式参数生成 MCP 配置并接入你的 MCP 客户端，
> 自动加载这个 APK，确认索引状态后开始分析。如果当前客户端不能动态加载 MCP，
> 请保存配置并说明需要重新加载客户端，不要声称已经连接成功。

参数说明：`--apk` 也可替换为单个位置参数；`--engine PATH` 指定引擎；
`--threads 1..64`（默认 4）；`--deobfuscate`、`--simplify-control-flow`、`--unflatten`
分别开启反混淆、控制流简化和去平坦化；`--background` 开启全量源码预生成
（默认按需生成，适合快速接入）；`--headless --help` 查看完整参数。
每个无头进程拥有独立工作区，不覆盖桌面偏好或 GUI 的 MCP 发现记录。
标准输出只承载 MCP JSON，分析日志写入标准错误；客户端关闭标准输入后会退出并清理工作区。
GUI 选中文本/当前类工具在无头模式不可用，请明确传入 `class_name`。

需要常驻 HTTP 服务时，用 `--headless --apk PATH --http-port 8650` 启动，
连接 `http://127.0.0.1:8650/mcp`；端口 `0` 自动分配，实际 URL 写入标准错误。
HTTP 模式持续运行，结束分析后停止进程。`--mcp` 单独使用仍是已有 GUI 的桥接模式；
自动启动分析必须包含 `--headless`。客户端配置文件位置及热加载能力由客户端决定。

## 构建和启动

需要 CMake 3.26+、C++17 编译器、Qt 6.5+ Widgets、Network 和 Concurrent。CLI 构建无需 Qt，
`GARLIC_BUILD_GUI` 默认关闭。

推荐使用仓库根目录的一键脚本，编译当前本地源码中的最新 GUI 及配套引擎：

```sh
./build_gui.sh
./build_gui.sh --debug              # 输出到 build-debug
./build_gui.sh --help               # 自定义 Qt 路径、输出目录和并行数
```

脚本可从任意工作目录调用，macOS 自动查找 Homebrew Qt。构建成功会显示版本、程序路径及
AI 文档路径；不会自动拉取 Git 或删除已有产物。`build/` 和 `build-debug/` 可删除后重建，
但其中的发布包、测试结果和日志也会被删除。

也可手动构建：

```sh
brew install qtbase
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DGARLIC_BUILD_GUI=ON -DCMAKE_PREFIX_PATH="$(brew --prefix qtbase)"
cmake --build build --parallel
open build/gui/garlic-gui.app
# 或带输入启动：
./build/gui/garlic-gui.app/Contents/MacOS/garlic-gui /path/to/app.apk
```

Linux 安装 Qt 6 开发包（如 `qt6-base-dev`），启用同一个 CMake 选项后运行
`build/gui/garlic-gui`。Windows 使用兼容 garlic 的 MinGW 和同架构 Qt 6 MinGW SDK。
实际构建、运行验证平台为 macOS arm64，其他平台尚未实测。

GUI 默认使用同目录下的 `garlic` / `garlic.exe`，构建时会自动复制。可以用
开发调试参数 `--engine /path/to/garlic` 更换；菜单始终使用内置引擎。语义功能需要使用本项目
0.5 配套引擎的丰富索引和源码位置映射，不能换成未经修改的上游 garlic。

## 乱码修复

DEX 和 CLASS 字符串使用 Modified UTF-8，其中 NUL 和 UTF-16 代理项不能直接
当作普通 UTF-8 交给 Qt。Kotlin `@Metadata(d1=...)` 又含有大量控制字符，因此
旧输出容易显示替代字符，旧注解转义还会生成无效的 `\0A`。

引擎现在统一处理注解、字符串常量和 Smali 字符串：正常中文保留，NUL / 控制
字符、引号、反斜杠和代理项正确转义。设置中的“Unicode 字符转义”可进一步把
非 ASCII 字符转义；也可仅隐藏代码视图中的 Kotlin Metadata。已有缓存需要
重新打开输入后生成。

## 重命名和项目

支持类、方法、字段的项目别名，支持撤销最近 100 次操作。标识基于原始类名、
成员名及描述符，不会对整段文本做全局替换；字符串和注释保留。带映射的成员
调用和声明会同步更新，Java / Smali、已打开标签、搜索和导出共享同一份别名。
构造方法保持 JVM / DEX 的 `<init>` 身份，通过重命名类更改 Java 显示名称。

“保存项目”生成 `.garlic.json`，保存全部输入路径、大小、修改时间及别名；“打开
项目”重新索引输入并恢复别名。退出前需保存希望保留的别名。项目文件不包含
APK 和生成的源码，不会修改、重打包或签名原 APK。

导出会在选定位置建立新目录，重新生成当前模式的全部源码并应用别名；类文件名
随别名更新，同时附带项目映射。取消 / 失败保留部分输出。别名是分析辅助功能，
不保证导出的整个工程能重新编译或汇编。

线程数直接传给 garlic 的 `-t`，前台请求和后台生成可能各占一个任务。包排除
和 Unicode 修改后重新打开输入生效。全项目搜索源码不计入按类缓存上限，关闭
项目时清理。默认按类缓存 2048 MiB、12 个标签、单文件限制 8 MiB。

反控制流平坦化参考 [eShard D810 的常量状态追踪和调度器边重定向](https://www.eshard.com/blog/d810-a-journey-into-control-flow-unflattening)，采用独立实现。
勾选后，在 DEX 模拟和 CFG 构造前，沿实际可达的唯一前驱追踪常量、寄存器搬移、
32 位整数运算和 Java UTF-16 `String.hashCode()`，处理 `goto → packed/sparse-switch`、
共享哈希入口及纯常量辅助函数返回值形成的条件。共享入口按入边分别求值，不能将文本上相邻的
常量当作整个 switch 的状态。支持负数 const/4 和 Java 整数溢出。
只接受完整字节码结构匹配的哈希包装器；仅在没有用户类初始化器时绕过已知字符串的哈希调用。
其他辅助调用保留，以保留副作用和异常。可变静态字段、多前驱合流、异常处理和不能证明状态的路径
保持原样。变换迭代最多 16 轮，每次求值有深度和节点预算；随后剔除不可达指令并重建控制流图。不会执行目标方法、加载目标类或修改原始 APK。设置持久保存，修改后源码缓存失效。
CLI 可用 `GARLIC_UNFLATTEN=1` 启用，默认关闭。

“反混淆”同时启用静态常量处理（CLI：`GARLIC_DEOBFUSCATE=1`）。参考
[D810 的表达式化简思路](https://www.eshard.com/blog/d810-deobfuscation-ida-pro)，独立实现
32 位整数加减乘除、取余、位运算和移位折叠，以及仅针对局部整数读取的 `x ^ x` / `x - x` 化简。
遵循 Java 溢出与移位规则，除零保持原样；不执行目标方法、不加载目标类，不做浮点或未知调用推测。
静态字符串支持 ASCII 字符数组构造、substring、concat、replace 的嵌套组合，以及常见的
`short[] + 起始位置 + 长度 + XOR key -> String` 字面量解码器。对控制流中合并的整数状态，
只尝试当前方法内有限的常量候选，并要求结果是可读文本；不会执行目标解密方法。
还原结果以 UTF-8 的 `/* decoded: "…" */` 显示，保留原表达式和对象身份，避免影响 `==` 或异常行为。
未知自定义加密算法、运行时密钥、非字面量数组、非 ASCII 索引语义及解密循环尚不支持；不能保证自动还原任意混淆字符串。
分析有递归深度、节点/字节预算和 64 KiB 字符串上限。

方法的代码区和类树右键菜单提供“复制为 Frida Hook”与“复制为 Xposed Hook”。模板按
原始 JVM/DEX 签名生成，支持重载、构造函数、内部类和数组；不会使用显示别名。
Frida 调用保存的 overload，Xposed 模板放入模块的 `handleLoadPackage` 并使用其 classLoader。
静态初始化器不生成模板。此功能只复制文本，不注入或执行 Hook。
测试用 `fixtures/Flattened.smali` 及其已组装的 `flattened.dex`（smali 3.0.9）覆盖循环、
负数稀疏键、默认分支和未知状态；CI 重新编译输出 Java 并执行返回值断言。

jadx 截图中的 AUTO / SIMPLE / FALLBACK、变量反混淆、Kotlin 名称恢复、常量替换、
访问修饰符策略、匿名类 / 方法 / Lambda 内联、finally / switch 恢复策略、dx/d8
转换、数值格式和类型迭代次数，没有可直接复用的 garlic 运行时选项。设置页采用左侧横向文字导航，“引擎能力”说明这些差异；当前继续使用 garlic 本身的处理流程，没有无效开关。

## MCP

工具划分参考 [jadx-mcp-server](https://github.com/zinja-coder/jadx-mcp-server)，由
本项目以 C++ 实现，与当前 GUI 项目共享数据，并非使用 jadx 的 Java 后端。

1. 在 GUI 打开输入文件，进入“首选项 → MCP”，勾选启用并保存。
2. 选择 stdio 或 HTTP，从同一页复制对应配置，加入 MCP 客户端配置。
3. 保持 GUI 打开。客户端启动的是同一个可执行文件的 `--mcp` 桥接模式。

示例（以设置页生成的实际路径和 socket 为准）：

```json
{
  "mcpServers": {
    "garlic": {
      "command": "/absolute/path/Garlic.app/Contents/MacOS/garlic-gui",
      "args": ["--mcp", "--socket", "garlic-gui-xxxxxxxxxxxxxxxx"]
    }
  }
}
```

stdio 使用当前用户可访问的本地套接字。HTTP 模式在 `127.0.0.1:8650/mcp`（端口可设置）
提供 Streamable HTTP 的 POST / JSON 响应，GET 返回 405。不需要 auth。绑定 IP 可设为 `0.0.0.0` 或 `::`，局域网客户端使用本机局域网 IP。
stdio 使用用户目录的绝对套接字和端点发现文件，客户端临时目录不同或旧 socket 参数不再阻止连接。
服务仍检查 HTTP Origin 和请求大小。两种传输共享当前 GUI 的工具与项目。
stdio 输出仅有 JSON-RPC，
日志写 stderr。支持 initialize、ping、tools/list 和 tools/call；源码 / 搜索 / 引用
请求异步处理，超时 300 秒。大型项目可重试查询已生成的源码。

工具包括：

- 当前界面：`fetch_current_class`、`get_selected_text`。
- 结构：`get_all_classes`、`get_package_tree`、`get_methods_of_class`、`get_fields_of_class`。
- 源码：`get_class_source`、`get_smali_of_class`、`get_method_by_name`。
- 搜索：`search_method_by_name`、`search_classes_by_keyword`（符号或代码）。
- 引用：`get_xrefs_to_class`、`get_xrefs_to_method`、`get_xrefs_to_field`。
- 修改：`rename_class`、`rename_method`、`rename_field`、`undo_rename`、`save_project`。
- 管理：`get_cache_stats`、`clear_cache`、`get_settings`、`set_settings`、`cancel_task`。

完整参数由 tools/list 返回。重载方法需要提供 `signature`，否则返回歧义错误。
类名支持 `demo.Main` 或 `demo/Main`；返回的符号 ID 始终保留原始身份。AI 重命名
会即时更新 GUI，可撤销。资源、调试器、局部变量 / 包重命名工具尚未实现，未对
客户端宣称支持。

## 引擎协议

```sh
# JSONL 类型、成员、引用索引，包含内部类
./build/garlic app.apk -I /tmp/classes.jsonl -o /tmp/index-output -t 2
# 按顶层类生成 Java；内部类随父类生成
GARLIC_SOURCE_MAP_DIR=/tmp/java-output \
  ./build/garlic app.apk -c demo/Main -o /tmp/java-output -t 2
# 按原始 DEX 类生成 Smali
./build/garlic app.apk -c 'demo/Main$Details' -s -o /tmp/smali-output -t 2
```

索引每行包含 `name`、`kind`、`flags`、`inner`、`methods`、`fields`、`refs`。
符号例如 `Ldemo/Main;->greet(I)Ljava/lang/String;`。可选环境变量：
`GARLIC_SOURCE_MAP_DIR` 生成 `.map.json`（UTF-8 字节范围），
`GARLIC_ESCAPE_UNICODE=1` 开启 Unicode 转义，`GARLIC_EXCLUDED_PACKAGES`
为分号分隔的 `/` 形式包前缀。找不到指定类时退出码非零。

## 边界

- 每个未命中的请求仍启动新引擎进程并重新解析输入，没有持久 DEX 解析会话；
  索引保存在 GUI 内存，按类源码可选内存或磁盘缓存。
- 索引解析、源码符号映射、引用查询、搜索及导出别名处理移到工作线程；类型树
  分批构建，成员按展开加载。超过 512 KiB 的代码暂不做语法高亮，保留查看、
  查找与导航，以避免整篇同步高亮阻塞窗口。这些措施不能保证任意损坏输入都
  无性能问题；CLI 崩溃仍以独立进程处理。
- 方法 / 字段映射来自引擎发射的表达式，Java 类型定位还辅以导入和类型上下文
  解析；复杂转换、动态调用、反射及局部变量没有完整语义保障。不会保证覆盖
  jadx 所有引用与重构能力，也不自动重命名整个方法覆写族。
- 多 DEX / split APK 中同名类仍按类名合并；无法分别选择重复定义。
- 内部类 Java 页面显示所属顶层类源码，Smali 是独立原始类；没有两种代码行号同步。
- 调试器和资源文本全局搜索尚未实现。GUI 的名称反混淆会为不可读的类、字段、方法生成稳定别名，
  局部变量会拒绝控制字符、零宽字符、组合标记、私有区字符和替换字符，并回退到类型名；上述别名
  只改变显示和导出映射，不改写原始 DEX。
- Garlic 原有的反编译错误可能保留。进程成功和源码生成不等于每个方法恢复成功。
  全项目搜索只覆盖成功生成且未超过大小限制的文件。

### Native ELF 与 Ghidra 伪代码

可以直接打开 ELF（包括无扩展名文件），也可以从资源树分析 SO。ELF 头、架构、入口和节表在后台独立读取，即使 Native 后端不可用也能查看。

Native 窗口中选择“Ghidra 伪代码”，点击“配置 Ghidra…”选择安装目录，然后重新分析。需要自行安装 Ghidra、该版本要求的 JDK（通过 JAVA_HOME 或 PATH），以及对应平台的 Ghidra native decompiler。应用不会捆绑 Ghidra，也不会执行目标文件。参考 [Ghidra Headless API](https://ghidra.re/ghidra_docs/api/ghidra/app/util/headless/AnalyzeHeadless.html)。

分析在独立进程进行，可停止；每个函数最多 10 秒，脚本最多 120 秒、2000 个函数、约 16 MiB 输出，整个进程最多 240 秒。达到限制会在结果中说明。界面按需读取前 8 MiB，可导出完整生成结果。伪代码属于静态分析结果，不保证等同于原始源码。

Windows x64 发布包显式收集 Rosemary DLL 的 GCC 运行库；临时 DLL 创建和加载使用 Unicode Windows API。Windows ARM64 目前没有仓库配套的 Rosemary 库，可使用独立 ELF 概览或配置兼容运行环境的 Ghidra；这不代表已经提供 ARM64 原生 Rosemary。Windows 修复尚需实际 Windows 机器验证。

### 数组恢复与条件分发链（2026-09-11）

修正 DEX `new-array` / `filled-new-array` 的维度与长度建模，以及 `fill-array-data`
按数组对象类型读取元素造成的 `new short[][]{null, ...}`。八种基本类型现在按 payload
宽度和元素类型解码；紧邻分配且长度一致时合并为初始化列表，其他情况以 `System.arraycopy`
表达原地填充，保留目标引用和未覆盖元素。静态 short 表仅作为解码注释的分析数据，生成源码
仍读取原字段，不能替换成每次重新分配的数组。浮点常量保留足够精度与非有限值的原始位模式。

参考 [eShard D810 的控制流恢复方法](https://www.eshard.com/blog/d810-a-journey-into-control-flow-unflattening)，
在 Dalvik CFG 上扩展有界反向状态追踪：合流的所有可达前驱给出同一值才传播，识别所有定义
一致的常量寄存器，并沿已知状态穿过连续条件比较分发链、重接入口边后重复清理。遇到未知值、
写寄存器、调用或追踪预算限制时停止；这不是移植完整 D810，也未实现通用路径复制或微码模拟。

自有 smali 回归经反编译、javac 编译和 Java 执行，覆盖条件链循环、合流、八种基本数组、
动态长度、原地填充及异常、静态引用共享、负零/极小值/NaN。两份真实 APK 全量生成正常。
算法助手应用包下的错误二维 short 初始化与 `(null)` 已消失；控制流统计仍为 246 个 switch、
11711 个 goto，说明本轮条件链扩展尚未进一步解决该样本的剩余复杂结构，不能仅凭样例通过
宣称其全部代码已恢复。

### 引用查询与搜索延迟（2026-09-11）

- 类索引发布前完成引用和符号索引，避免界面显示可用后，首次 X 查询仍等待全量引用构建锁；覆盖关系移到后台搜索预热阶段完成。
- 引用源码按文件建立声明范围、目标引用和行号表；对同一来源方法复用匹配结果，避免每条字节码引用反复扫描整份源码。

- 别名版本哈希和类别名查找表按版本缓存，消除大项目每次搜索重建几十万个别名 JSON 的开销。重命名和撤销会使预热状态失效。
- 源码映射复用类型上下文正则，跳过已覆盖的 token；别名替换一次拼接输出。反混淆后的搜索文本按别名版本缓存在当前临时工作区，跨范围切换和内存缓存淘汰后不再重复解析映射；清理源码缓存或关闭项目时一并清理。
- 预热使用专用索引模式，并明确区分“源码生成完成”与“搜索索引就绪”。实际查询取消预热后，空闲时会恢复剩余准备。

反混淆、去平坦化和控制流简化全部开启，索引就绪后的代码／注释／组合首次查询分别为
153／152／154 ms，`public` 返回前 1000 条约 101 ms，`getSharedPreferences` 返回 63 条约 252 ms。

实际命中的查询（1000 条常见词、99 条 API 名搜索）均约 50 ms，初次整包准备约 8.4 s。

一秒指标是索引就绪后的查询延迟，不包括首次整包反编译及索引构建。默认设置的首次源码搜索
从约 16.6 s 降到约 9 s；`base.apk` 全开反混淆并生成别名搜索文本的整包准备实测约 102 s。
超大结果全集和任意复杂正则没有一秒完成保证。性能测试覆盖实际返回结果、范围切换、重命名／撤销失效，
同时保留完整解析耗时，不把它混成查询耗时。

### 大型 APKS 五秒内打开目录（2026-09-11）

对至少 128 MiB 的单个 APKS，首次打开改为分阶段加载。第一阶段读取全部类名、类型和
内部类标记，跳过方法代码和静态初值解析；目录节点脱离模型批量构建，完成后发布分支，

第二阶段在独立任务中生成完整成员、继承和引用索引，完成后一次替换索引并刷新成员目录、
